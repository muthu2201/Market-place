# Capacity

Measured numbers, and what they mean. Every figure below was produced by
`ops/stress-test.sh` against the real system — no mocked provider at the
application boundary, no disabled controls.

## Test conditions

**Deliberately hostile.** A 4-core container ran *everything at once*: the API,
the worker, PostgreSQL 16, and the gateway simulator speaking the Razorpay wire
protocol. They competed for the same four cores throughout.

Production would separate these. The point of measuring this way is that the
numbers are a floor: any real deployment has more headroom than this, and a
result obtained on a dedicated 16-core box would tell you nothing about the
system's behaviour under contention.

Load was generated by `cmd/loadgen` with distinct client IPs per worker
(`203.0.113.0/24`) so rate limiting applied as it would to distinct users
rather than shedding a single synthetic address.

## Results

### Read path — catalogue browsing and search

| Metric | Measured |
|---|---|
| Throughput | **2,885 req/s** |
| p50 latency | 16 ms |
| p90 latency | 34 ms |
| p99 latency | 55 ms |
| Errors | **0** |

### Commerce path — checkout, payment, confirmation, entitlement

| Metric | Measured |
|---|---|
| Completed purchases | **53.9/s** |
| Total request rate | 273 req/s |
| Errors | **0** |

Each completed purchase is five round trips — checkout, begin payment, the
simulated provider interaction, confirm, and entitlement issue — with the full
tax computation, two ledger entries totalling seven or eight lines, an audit
entry, a turnover delta and outbox messages, all inside one transaction.

**53.9 purchases per second is 4.6 million per day.** For a launching
marketplace, the constraint is finding buyers, not serving them.

### Invariants under load

Checked after the run, not before:

| Invariant | Result |
|---|---|
| Ledger trial balance nets to zero per currency | **PASS** |
| Audit hash chain verifies end to end | **PASS** |
| Orders reconcile against ledger postings | **PASS** |
| Application healthy and serving | **PASS** |

Zero errors *and* all invariants holding is the result that matters. Either
alone would be meaningless: a system can be fast and wrong, and it can be
correct while shedding a fifth of its traffic.

## The bottleneck is Argon2id, deliberately

| Operation | Cost |
|---|---|
| Argon2id hash (64 MiB, t=2, p=1) | **~123 ms** |
| Money multiply-divide with rounding | 6.2 ns, zero allocations |

Password hashing dominates authentication and is *supposed* to. 123 ms is
imperceptible to a person logging in and ruinous to someone testing a credential
list. Registration and login therefore scale differently from everything else,
and the architecture accounts for it:

- Rate limiting sits **before** authentication in the middleware chain, so an
  unauthenticated flood is shed before reaching the expensive step.
- `RATE_LIMIT_LOGIN_BURST` is capped at 200 in production, because a large burst
  defeats the control.
- `Parallelism` is **1**, not `min(4, NumCPU)`. Parallelism helps a single hash
  finish sooner; on a server running many concurrent hashes it only multiplies
  the contention. Under load with `p=4`, registration p50 was **13.1 seconds**.
  With `p=1` it is 123 ms per hash and the box stays responsive.

That last change is the clearest example of a tuning decision that looks right in
a benchmark and is wrong in a server.

## How the numbers got this good

They did not start here. The first stress run produced **5.8% 500s** on checkout
and confirm, from serialization failures under `REPEATABLE READ`. Six concurrency
defects were found and fixed — see
ADR [0012](../adr/0012-read-committed-isolation.md) for all six. The largest
effects:

| Defect | Effect of the fix |
|---|---|
| `REPEATABLE READ` everywhere | 5.8% error rate → 0 |
| Order numbers from the gapless invoice allocator | Removed a full serialisation point from every checkout |
| Single platform-wide turnover row | Removed the last hot row from the commerce path |
| `INSERT … DO NOTHING` then `SELECT` on seller accounts | Removed an intermittent failure that only appeared under concurrency |

Every one of these was invisible to code review and to single-threaded tests.

## Scaling

**Stateless tier.** `api` and `worker` scale horizontally without coordination:
no sticky sessions, no local cache, no in-memory state that would need
invalidating. Sessions are database rows.

**Database.** One primary is the write ceiling
(ADR [0002](../adr/0002-postgresql-as-the-backbone.md)). Available before it
binds, roughly in the order they become worth doing:

1. Read replicas for the catalogue and search paths — the bulk of read traffic,
   and tolerant of replica lag.
2. Partition `audit_log`, `outbox_messages` and `journal_lines` by time. These
   are append-only and grow without bound; everything else is comparatively
   small.
3. `PgBouncer` in transaction mode, if connection count rather than throughput
   becomes the constraint.
4. Only then, shard. Almost certainly never.

**Delivery does not scale with the application.** Download bytes go from R2 to
the buyer directly (ADR [0014](../adr/0014-object-storage-choice.md)), so a large
asset or a viral product consumes no application capacity and no application
egress.

**In-process rate limiting is per-instance.** N instances give N× the intended
limit. `rate_limit_allow()` exists in the database for the multi-instance case
and should be switched on before the second instance, not after.

## What to watch

| Metric | Meaning | Act when |
|---|---|---|
| p99 latency by route | The honest user-facing number | Sustained above 200 ms |
| Database connection utilisation | The real capacity ceiling | Above 70% |
| `40001` / `23505` retry rate | Contention returning | Rising trend, at any level |
| Outbox dispatcher lag | The worker falling behind | Above 60 s |
| Argon2id calls per second | Authentication load | Above ~20/s per instance |
| Replica lag | Failover data-loss exposure | Above 5 s |

The retry-rate row is the early warning. Contention shows up there long before
it shows up in latency, and long before it shows up as errors.

## Reproducing

```bash
ops/stress-test.sh
```

It brings up the database, applies migrations, seeds a catalogue, starts the
gateway simulator, the API and the worker, runs both load profiles, then
verifies every invariant and prints the table above. Run it before any release
that touches the commerce path.
