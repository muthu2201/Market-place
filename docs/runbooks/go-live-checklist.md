# Go-live checklist

Complete every item before the first real payment. Items marked **BLOCKING**
must not be waived.

## 1. What the test suite cannot prove

The end-to-end suite runs against `gatewaysim`, which speaks the real Razorpay
wire protocol — the same paths, JSON shapes and HMAC schemes — so the real
adapter, real signature verification and real error classification are all
exercised. Three things it deliberately does not simulate must be exercised
against the provider's own sandbox:

- [ ] **BLOCKING** Linked-account KYC activation, and the holds that follow from it
- [ ] **BLOCKING** Real bank settlement timing and UTR issuance
- [ ] **BLOCKING** The provider's own rate limits and outage behaviour

Run one real end-to-end purchase in the provider's sandbox and reconcile it
against the journal, line by line, before opening to the public.

## 2. Regulatory posture

- [ ] **BLOCKING** Confirm with the provider, in writing, that the chosen
      settlement model keeps the platform out of the flow of funds
- [ ] **BLOCKING** `PLATFORM_GSTIN` set and verified against the GST portal
- [ ] TAN registered for TDS remittance under s.194-O
- [ ] GSTR-8 filing process agreed with the accountant, with a dry run on test data
- [ ] Route eligibility evaluated (`EvaluateRouteEligibility`); if ineligible,
      the bridge adapter's separate payout reconciliation is documented and staffed
- [ ] Grievance officer appointed and published, per the CP (E-Commerce) Rules
- [ ] Published pages live and correct: `/legal/ranking`, `/legal/fees`,
      `/.well-known/security.txt`
- [ ] Privacy notice and consent records match the `consents` table's categories

## 3. Configuration

`APP_ENV=production` makes eighteen unsafe settings fatal at boot. Verify the
process actually starts, then confirm each of these is deliberate:

- [ ] **BLOCKING** `DATA_KEK` — 32 bytes, generated by a CSPRNG, stored in a
      KMS/HSM, **backed up separately from the database**
- [ ] **BLOCKING** `SESSION_SIGNING_KEY`, `CSRF_SIGNING_KEY` — distinct 32-byte keys
- [ ] **BLOCKING** `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET` — distinct
      secrets; confirm the code path for each is the correct scheme
- [ ] `APP_PUBLIC_BASE_URL` https, matching the certificate
- [ ] `HTTP_TRUSTED_PROXY_CIDRS` — exactly the edge ranges, nothing wider
- [ ] `SETTLEMENT_HOLD_DAYS` ≥ 7 and agreed commercially
- [ ] `DOWNLOAD_URL_TTL` short — minutes, not hours
- [ ] `METRICS_TOKEN` set and distributed only to the scraper
- [ ] `STORAGE_DRIVER=s3`, pointing at the production bucket, in the intended region
- [ ] `MAIL_DRIVER=smtp` with a verified sending domain (SPF, DKIM, DMARC)

## 4. Data and backups

- [ ] **BLOCKING** Restore a backup into a scratch database and run
      `/internal/verify/consistency` against it. An untested backup is not a backup
- [ ] **BLOCKING** KEK backup tested — restore it into a scratch KMS entry and
      decrypt one known ciphertext. **Losing the KEK loses every subject's data**
- [ ] PITR configured with WAL archiving; recovery-window target documented
- [ ] `migrate` run against production, with drift detection clean
- [ ] Replica streaming, and promotion rehearsed at least once

## 5. Observability

- [ ] Metrics scraped and dashboarded, labelled by route template
- [ ] Alerts wired for every row in
      [../arch/07-failure-modes.md#detection](../arch/07-failure-modes.md)
- [ ] **BLOCKING** Trial-balance and audit-chain alarms tested by deliberately
      tripping them in staging. An untested alarm is an assumption
- [ ] Log aggregation with request-ID correlation
- [ ] `/readyz` wired to the load balancer

## 6. Security

- [ ] **BLOCKING** TLS termination with HSTS; certificate auto-renewal verified
- [ ] Security headers verified on a live response, not asserted from code
- [ ] Rate limits confirmed under a synthetic burst against the deployed system
- [ ] Seller 2FA enforced (production refuses to disable it — confirm it is real)
- [ ] Dependency scan clean; the module list is short enough to read in full
- [ ] `security.txt` contact monitored by a person

## 7. Operational readiness

- [ ] On-call rota exists and knows these runbooks exist
- [ ] Every runbook in this directory read once, before it is needed
- [ ] Rollback procedure documented and rehearsed
- [ ] Support has a written answer for "where is my money", derived from
      `ReleaseResult.HeldReasons`
- [ ] Grievance SLA clock confirmed against `grievance_sla_watch`

## 8. Commercial

- [ ] Fee schedule inserted with the correct `announced_at` — the 90-day
      constraint means this cannot be corrected quietly later
- [ ] Seller terms reference the ranking and fee pages by URL
- [ ] Refund policy consistent with what the code actually does
- [ ] Chargeback exposure modelled against `SETTLEMENT_HOLD_DAYS`
